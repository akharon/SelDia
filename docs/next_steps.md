# SelDiA — Next Steps

**Date:** 2026-07-16
**Purpose:** The single actionable roadmap. Supersedes the old `docs/plan.md` (24-week build plan, now complete) and `docs/improvement_request.md` / `docs/review-2026-07-14.md` (rendering-quality pass, now mostly resolved — see §3). Strategic reasoning behind the priorities lives in [market.md](market.md).

---

## 1. The strategic bet (from market.md)

> **SelDiA is not a third diagram format. It is the diagram *engine* that runs everyone's — Mermaid and PlantUML included.**

The category change, not a feature fight: a format war against Mermaid (native GitHub rendering, total LLM training coverage) is unwinnable — it's D2's four-year losing script. Instead, demote the competition to input formats. Users keep their Mermaid; SelDiA sits underneath as the engine that parses, validates, queries, and keeps diagrams true as the system drifts. That layer requires an IR, diagnostics, and round-tripping — the one set of assets SelDiA has that neither competitor's architecture can grow.

The pitch: **"Keep your Mermaid. SelDiA keeps it true."** Mermaid is a format, PlantUML is a tool, SelDiA is the engine. The SelDiA DSL remains the engine's native format for those who want its full power — not the price of admission.

Everything in Tier 1 below serves that bet directly. Tier 1 and Tier 2 have now shipped; Tier 3 remains deliberately resisted.

## 2. Roadmap

### Tier 1 — do these next, in order

**1. Mermaid import — foundation landed, not finished.** This is the engine positioning made executable, and it must be excellent rather than demo-grade (a leaky bridge re-opens the format war).

*Shipped:* a Mermaid→IR frontend ([`core/src/import/mermaid.ts`](../packages/core/src/import/mermaid.ts)) covering **flowchart, sequence, class, ER, state, gantt, pie, gitGraph, and mindmap** — the bulk of real-world Mermaid. It's a true frontend (source→IR directly, not a translation through SelDiA DSL text), joined to the pipeline by `engine.compileIRSync(ir)`. Reachable two ways: ` ```mermaid ` fences now render through SelDiA in the Markdown preview, and `seldia mermaid <file.mmd>` renders from the CLI. Covered by 36 importer tests + 9 preview tests.

*The safety property to preserve:* an unimportable block **falls back to the default fence**, so installing SelDiA can never make a Mermaid document render worse than not having it. Never replace that fallback with a SelDiA error box in a document whose author never asked for SelDiA.

*Shipped since:* **Subgraphs** — the Mermaid importer now parses `subgraph`/`end` (including nesting) into `IRGroup`s, and the engine gained group support end-to-end: a bounding-box layout post-pass over each group's member nodes (`engine.ts` `layoutGroups()`), inclusion in viewBox bounds, and a renderer (`renderGroup()` in `custom-renderers.ts`) that draws a background box + label behind the member nodes. This was bigger than it looked — `groups` existed on the IR type but nothing in the layout engine or renderer consumed it, for *any* diagram type, DSL included. It's now general engine capability, not Mermaid-specific.

*Shipped since:* **State, gantt, pie, gitGraph, mindmap importers.** Each target IR shape was already carried by the engine's custom layout functions (`layoutGantt`, `layoutMindmap`, `layoutGitgraph`, `parseChartCategory`) — those parse structured info (dates, branch names, category values) back out of a plain node label, so the importers just had to produce labels in the vocabulary each parser expects (e.g. gantt tasks as `"Design: Jan 6-9"`, pie slices as `"Dogs\nDogs: 386"`, git commits as `"branch: message"`) rather than populate `data` fields directly. State diagrams needed one wrinkle: Mermaid's `[*]` pseudostate is shared syntax for both start and end, so each occurrence is split into its own synthetic node — collapsing them onto one shared node would cross-wire unrelated transitions. **Journey was deliberately skipped**, not deferred by omission: there is no `DiagramType.JOURNEY`, no plugin, and no renderer anywhere in the engine, so it isn't an importer gap, it's a net-new diagram type (Tier 3 territory per the "resist more diagram types" principle above) — falls through to the default-fence fallback like any other unsupported type.

*Shipped since:* **Styling directives.** The flowchart importer now parses `style nodeId ...`, `classDef name ...` + `class nodeId,... name`, and `linkStyle N|default ...`, mapping the CSS-like property list (`fill`, `stroke`, `stroke-width`, `stroke-dasharray`, `color`, `opacity`) onto `IRNode.style` / `IREdge.style`. `classDef` styles apply first, then a same-node `style` line overrides them, matching Mermaid's own cascade — resolved as a post-pass over collected `class` assignments and `linkStyle` declarations, since both directives conventionally appear after the nodes/edges they target.

*Shipped since:* **Mermaid export — the return leg.** [`core/src/export/mermaid.ts`](../packages/core/src/export/mermaid.ts) emits Mermaid source from IR for the same nine types the importer covers, so output can still ride GitHub's native rendering. It's best-effort by design: shape delimiters, class relation tokens, and label vocabularies (gantt dates, pie slices, git branches) are inverted from the importer's own mappings, and anything with no Mermaid equivalent (arbitrary `data`, unsupported diagram types) is dropped rather than guessed at — `exportMermaid()` returns `null` for a type it doesn't cover instead of emitting misleading output. Verified via round-trip tests (import → export → re-import → compare structure) rather than exact-text assertions, since Mermaid has many valid spellings for the same structure; also confirmed the re-imported IR still renders to real SVG through `engine.compileIRSync()`, not just that it re-parses. One accepted lossy edge: gantt dates round-trip without a year (the label vocabulary never carried one), so export assumes the current year.

*Shipped since:* **A fidelity corpus.** [`core/test/fixtures/mermaid-corpus/`](../packages/core/test/fixtures/mermaid-corpus) holds nine hand-curated, realistic Mermaid samples — a CI/CD pipeline with nested subgraphs and styling directives, an auth sequence, a domain class model with a stereotype, a full ER schema with PK/FK annotations, an order state machine, a multi-section gantt with a milestone, a market-share pie, a two-branch gitGraph with merges, and a three-level mindmap — the kind of thing a real repo's docs actually contain, not minimal unit-test snippets. [`mermaid-fidelity.test.ts`](../packages/core/test/mermaid-fidelity.test.ts) checks each one three ways: zero import diagnostics, structural counts read directly off the source (nodes/edges/groups/styled elements), and a full render to real SVG through `engine.compileIRSync()`. That third check is what catches the "renderer silently drops structure it never reads" bug class that IR-shape assertions alone missed previously (class members, ER attributes). Pulling samples from actual public repos (vs. curated-but-hand-written) was considered and deferred — it needs network access this pass didn't use — so the corpus is representative rather than sourced; expanding it with real fetched samples remains a smaller future step, not a blocker.

*Shipped since:* **CLI export.** `seldia export <file.sld> --to mermaid [-o <path>]` wires `exportMermaid()` into the CLI: it runs the file through the engine's own `parse` → `analyze` → `transform` steps to get IR, calls `exportMermaid(ir)`, and either prints the Mermaid text to stdout or writes it to `-o/--output`. Types outside the exporter's coverage (`isMermaidExportable() === false`, e.g. C4, BPMN) print a clear error and exit non-zero rather than emitting nothing or misleading text. Covered by [`cli/test/export.test.ts`](../packages/cli/test/export.test.ts), which spawns the built binary.

*Shipped since:* **Preview-pane export action.** `seldia.exportToMermaid` in `packages/vscode-ext` mirrors the CLI's own pipeline — `engine.parse` → `analyze` → `transform` to IR, then `exportMermaid(ir)` — rather than reimplementing it, so the two entry points can't drift. It's reachable three ways: command palette (`SelDiA: Export Diagram to Mermaid`, enabled when `editorLangId == seldia`), the `.sld` editor context menu (next to the existing `seldia.exportDiagram` entry), and a per-block "Export to Mermaid" CodeLens above fenced ` ```seldia ` blocks in Markdown — the last reuses the `sourceArg` pattern `seldia.exportDiagram`'s own CodeLens already established, so a block can be exported without making it the active editor. Output goes through `showSaveDialog` filtered to `.mmd`, matching `exportDiagram`'s existing SVG/PNG/PDF save-dialog convention rather than inventing a new output mechanism (untitled document, webview panel) for just this one format. Unsupported types (`isMermaidExportable() === false`) surface a `showErrorMessage` naming the diagram type instead of a silent no-op or a crash.

**2. Rendering-distribution path — the Action shipped, viewer promotion is docs-only and shipped too.**

*Shipped:* **`seldia render`** ([`packages/cli/src/index.ts`](../packages/cli/src/index.ts)), a repo-wide batch command that scans a directory for standalone `.sld` files and ` ```seldia ` / ` ```seldia-<type> ` fenced blocks inside `.md` files, compiles each through the same `engine.compile()` pipeline `compile` already uses, and writes one SVG per diagram into an output directory. The fence-scan ([`packages/cli/src/scan.ts`](../packages/cli/src/scan.ts)) is a plain-Node reimplementation of the vocabulary `packages/vscode-ext/src/markdown/detector.ts`'s `BlockDetector` already established — same fence patterns, but walking the filesystem instead of a live `vscode.TextDocument`, since a GitHub Action has no editor to hook into and `BlockDetector` is hard-coupled to the `vscode` API. Multi-fence files get a numeric slug suffix (`notes-0.svg`, `notes-1.svg`) so nothing collides. Covered by 11 unit tests on the scanner ([`scan.test.ts`](../packages/cli/test/scan.test.ts)) and 6 CLI-level tests spawning the built binary ([`render.test.ts`](../packages/cli/test/render.test.ts)), including a mixed-success case (one good diagram, one syntax error) asserting the good one still gets written and the process still exits non-zero.

*Shipped:* **The `seldia-render` GitHub Action** ([`.github/actions/seldia-render/action.yml`](../.github/actions/seldia-render/action.yml)) — a composite action that installs `@seldia/cli` and shells out to `seldia render` (never reimplements IR compilation), then optionally commits the output directory back if anything changed. A copy-paste example workflow lives at [`.github/workflows/render-diagrams.yml.example`](../.github/workflows/render-diagrams.yml.example) — shipped as `.example` rather than a live workflow because turning it on unconditionally in this repo would try to render every intentionally-invalid test fixture and doc sample under `examples/`, not real diagrams meant for distribution. **Not tested in this environment:** the composite steps themselves (checkout, npm install, git add/commit/push) and real GitHub-hosted execution — no runner available here. The core rendering logic they call is tested (see above); the Action wrapper needs a manual run in a real repo before a team relies on it for CI. See [`.github/actions/seldia-render/README.md`](../.github/actions/seldia-render/README.md) for the full contract.

*Shipped:* **`<seldia-viewer>` promotion — documentation only, the component itself needed no code changes.** It was already fully functional and shipped in `@seldia/web` (built, in `dist/`), just underdocumented: the root README mentioned it in a features bullet with no usage example, and `packages/web/README.md` had install/usage snippets but no framing for *why* you'd reach for it. Added a "Getting diagrams out of the editor" section to the root [README.md](../README.md) that pairs the two rendering-distribution paths explicitly — render-to-SVG-in-CI (via the Action) for surfaces that render plain `<img>`/SVG (GitHub itself, most docs sites), `<seldia-viewer>` for surfaces that can run a script but aren't rendered by GitHub (internal wikis, a runbook served from your own app) — plus a copy-paste embed snippet. Deliberately did not add a DOM test harness for the Lit component: `@seldia/web` has no jsdom/happy-dom test environment configured today and none of its three custom elements have any existing tests, so adding one is a larger scope decision than "promote via docs" calls for — noted here rather than silently skipped.

**3. Agent-facing diagram interface — shipped.** New package [`packages/mcp`](../packages/mcp) (`@seldia/mcp`), an MCP server (stdio transport, bin `seldia-mcp`) built on `@modelcontextprotocol/sdk`, reusing `@seldia/core`'s own `createEngine()` pipeline rather than reparsing. Tools: `load_diagram`, `validate_diagram`, `query_diagram` (dependsOn/dependedOnBy via IR edge traversal), `list_nodes`, `list_edges`, `mutate_node` (patches label/style on a flat `id (Shape) "Label" { key: value }` declaration, refuses nested attribute blocks rather than mis-editing them), `write_diagram` (stubbed — no general IR→DSL serializer exists yet, returns a clear `ok: false` rather than guessing). Mermaid inputs are read-only, consistent with Mermaid's position as an input format. 13 tests against a real fixture, all passing; no regressions in `@seldia/core`/`@seldia/cli`. Remaining gap: the general full-IR write-back serializer.

**4. Persistent manual positions — shipped.** Root cause found: `SelDiAInteractiveProvider.applyDslPatch` never wrote drag positions to disk — one branch nuked the whole document, the other silently no-op'd — so every recompile re-ran auto-layout from source that never had the position. Fixed via a new pure serializer, [`packages/vscode-ext/src/edit/position-patch.ts`](../packages/vscode-ext/src/edit/position-patch.ts), which merges `x`/`y` into a node's existing attribute block (or rewrites a legacy nested `layout: {x,y}` block) without clobbering other keys, applied through a real `WorkspaceEdit`. The suspected blank-preview-on-drag race (§3) was investigated and found **already mitigated**: the Markdown preview is read-only by design (no drag handler exists there — `edit/commands.ts` documents this as the deliberate fix for that exact race), and all dragging happens in the separate `.sld`-only `SelDiAInteractiveProvider` webview, which never keys state off a content hash. 9 new round-trip tests passing; no new regressions (the 8 failures in `plugin.test.ts` are the pre-existing, unrelated `id: (Shape)` parser bug).

### Tier 2 — shipped

**1. Theme/palette swapping without a fork — shipped.** `PaletteOverride` + `BUILTIN_PALETTES` (`default`, `dark`, `high-contrast`) in [`design-system.ts`](../packages/core/src/render/design-system.ts), selected via `config.render.theme` (name) or `config.render.palette` (explicit color map), and wired to the CLI as `--theme`. The renderer reads the override through live getters on `DS.neutral` and through `typeSwatch()`/`roleSwatch()`, so no renderer code forks per theme. Two bugs found and fixed while verifying: `roleSwatch()` bypassed the override entirely (a dark theme left `[Start]`'s light-mode green fill on a near-black background — role colors now route through `applyOverride()` like type accents do), and the override is cleared after each compile so it can't leak between engines.

**2. Edge editing in Edit mode — shipped.** Add/delete edges from the `.sld` webview, reusing the existing `WorkspaceEdit` patch path rather than rewriting the document.

**3. Macro/include system — shipped.** `include "other.sld"` is expanded by a pure text preprocessor ([`macro/include.ts`](../packages/core/src/macro/include.ts)) before the DSL parser runs, so it needs no tokenizer/parser change and a source with no directives round-trips unchanged. Paths resolve relative to the including file; missing and circular includes are hard parse errors reported at line 1 (a successful `Result<DiagramAST>` has no warnings channel to attach a soft note to).

**4. Export to semantic formats — shipped.** [`export/bpmn.ts`](../packages/core/src/export/bpmn.ts) (BPMN 2.0 XML, including BPMNDI shape bounds from the IR's own layout) and [`export/sql-ddl.ts`](../packages/core/src/export/sql-ddl.ts) (`CREATE TABLE` + PK/FK constraints), wired as `seldia export --to bpmn|sql-ddl`. Both follow `mermaid.ts`'s best-effort contract: return `null` for a type they don't cover rather than emitting misleading output. Two real bugs surfaced here: the BPMN *plugin* discarded the documented `(event) [task] {gateway}` shape vocabulary and collapsed every node to `task` (so a whole process rendered as a flat wall of tasks — now inferred from shape, with start/end settled from edge topology since `(…)` is one shape for both), and the SQL exporter ignored an author's explicit `id: UUID` annotation in favour of a column-name guess (declared types now win).

**5. Diagram diffing for PR review — shipped.** `seldia diff <old.sld> <new.sld> [--format json]` reports structural IR changes (nodes/edges added/removed/changed) and exits non-zero on any diff, mirroring `diff`'s own convention for CI. Fixed while verifying: `--format json` returned early and always exited 0 (so a CI drift check using it could never fail), and the decorative CLI banner printed to **stdout**, corrupting any piped machine-readable output — it now goes to stderr, which also unbreaks `export --to mermaid | …`.

### Tier 3 — resist for now

**More diagram types.** The IR already has 30 `DiagramType` variants and SelDiA is still losing to tools with half that. Breadth is not the constraint; distribution is. Adding type 31 is the most comfortable and least useful thing to do next — don't.

## 3. Known technical debt (carried from prior internal review)

Most items from the rendering-quality pass (per-type visual grammar, `\n`→`<tspan>` line breaks, class compartments, zoom clipping, emoji→icon toolbar) are **done** — verified against current code, not assumed. What's still open:

- ~~**Tokenizer can't parse nested object values.**~~ **Fixed.** The brace-stack context tracking was already in place but mis-indexed: the classifier read `tokens[length-2]` for the token before a title STRING *after* the `{` had already been pushed, so for the canonical header `diagram <type> "Title" {` it never matched `KW_DIAGRAM` and classified the diagram's own **body** brace as `attr`. That made `inAttrContext()` true for every statement in the file, silently demoting the diamond-shape form `id: {Gateway?}` to a nested-object-value brace. Fixed the off-by-one and taught the classifier the `diagram <type> "Title" {` shape. Both forms now parse together: `id: {Gateway?}`, `a: (Start) { x: 300, y: 200 }`, and `a: (Start) { layout: { x: 300, y: 200 } }`.
- ~~**Pre-existing parser bug: `id: (Shape)` colon syntax.**~~ **Fixed** — same root cause as the tokenizer item above (it was specifically `id: {…}`, the brace/gateway form; `id: (…)`, `id: […]`, and `id: "…"` always worked). This resolved the 8 long-standing `plugin.test.ts` failures; that suite is now fully green.
- ~~**`.sld` vs `.seldia` extension mismatch.**~~ **Fixed.** `.sld` is canonical (it's what the VS Code extension registers and `examples/` uses); `docs/user_guide.md` and both `seldia-dsl` SKILL.md copies were normalized. The one surviving `.seldia` mention — the Action's `extra-extensions` input — is a legitimate example of a *custom* extension, not a claim about the default.
- ~~**`@seldia/render`, `@seldia/layout`, `@seldia/interaction` are unused.**~~ **Resolved.** `@seldia/render` and `@seldia/layout` were genuinely dead and were deleted in `d84b7bf`; the stale README note claiming all three are unwired is corrected. `@seldia/interaction` is **not** dead — the VS Code extension's Edit mode uses it for zoom/pan, selection, and undo/redo.
- ~~**Diagram container chrome vs. native VS Code look.**~~ **Fixed.** The always-on border + toolbar band was the last of the "bolted-on widget" weight. An idle diagram is now pure content — no border, no background, no reserved toolbar row — so it sits in the document flow like an embedded image or a rendered table. The controls (mode switch, zoom, export) became affordances rather than chrome: a faint frame plus a compact rounded toolbar overlay in the top-right fade in only on `:hover`/`:focus-within`, the same pattern as GitHub's on-hover code-copy button. The toolbar is `position:absolute` so revealing it never reflows the SVG. Error boxes and code mode keep a permanent frame (an error must always be visible; the code panel is an editing surface, not idle content). CSS-only change in [`seldia-preview.css`](../packages/vscode-ext/media/seldia-preview.css); verified by rendering the preview markup to PNG in both idle and hover states.
- ~~**Blank-preview-on-drag risk.**~~ Investigated during Tier 1 item 4: confirmed already mitigated, not a live risk — see item 4 above.
- ~~**MCP `write_diagram` has no general serializer.**~~ **Fixed.** [`sld-serialize.ts`](../packages/mcp/src/sld-serialize.ts) turns a full `DiagramIR` back into `.sld` source, so `write_diagram` now supports arbitrary structural mutation (new nodes/edges), not just the single-line label/style patches `mutate_node` does. It emits the `<shape-keyword> id: "Label"` node form and `-->`/`<-->` edges — chosen over bracket delimiters (`{Q?}`, `<H>`) because the keyword form is the one spelling that round-trips for *every* shape (some brackets only parse behind a colon; hexagon `<H>` doesn't tokenize as a shape at all). It follows `export/mermaid.ts`'s best-effort contract: types whose grammar lives in a label vocabulary the parser decodes structurally (gantt/charts/mindmap/gitgraph/sankey) return `null` and `write_diagram` reports "not serializable" rather than corrupting them. Two safety properties: the emitted DSL is re-parsed through the engine before anything is written, so a serializer bug can never leave an unreadable file on disk; and group membership is now re-emitted as real `group "Label" { … }` blocks (nested groups nest via `childGroupIds`), because the parser bug that used to drop group bodies is fixed (below). 4 new round-trip tests (17 total in `@seldia/mcp`, all passing), asserting nodes/edges/shapes survive a disk round trip and that non-serializable types and Mermaid files are refused without touching the file.

  *Fixed:* the DSL flowchart transform used to drop nodes declared inside a `group "…" { … }` body — they never reached `ir.nodes`. `flowchart.ts`'s `transform()` now recursively walks group bodies, emitting the child nodes/edges as real IR and contributing an `IRGroup` with `childNodeIds`/`childGroupIds` — the same shape the Mermaid `subgraph` importer produces, so group layout/render consumes DSL-authored groups identically. Three group-body tests in `parser.test.ts` cover node emission, membership, and nesting.
- ~~**Shipped examples don't parse: the `participant` keyword doesn't exist.**~~ **Fixed** — and the diagnosis above was wrong on every count, which is worth recording. `participant` was a red herring: it was never the thing that broke the file, and every example now compiles to real SVG. There were **four** independent bugs stacked behind the one misleading `Line 1: No diagram declaration found`:
  1. **`checkSyntax` read the raw first word of the source** to find the diagram declaration. Every file in `examples/` opens with a `// ---` comment banner, so the check saw `//`, decided there was no declaration, and rejected the file *before the parser ran* — which is why the error always pointed at line 1 regardless of the real problem. It now skips comments/blank lines like the tokenizer already did, and reports the line it actually examined.
  2. **Typed node decls didn't accept a colon.** The `shape id "Label"` form (`person customer "X"`) existed, but the spelling the docs and examples use (`person customer: "X"`, `participant user: "User"`) wasn't dispatched. `participant` was also genuinely missing from `SHAPE_KEYWORDS` — a one-word fix, not the blocker it was billed as. `data.typeKeyword` still carries the original word, so C4's `system_Ext` semantics survive.
  3. **Unquoted edge labels ran to the closing brace.** With no NEWLINE token, the label loop's only terminators were `EOF`/`}`/`diagram`, so `a -> b: GET /authorize` swallowed *every following statement* into one label — the OAuth example silently produced **1 edge instead of 11**. Labels are now bounded to their own line, and re-joined from token columns so `GET /authorize` no longer comes back as `GET / authorize`. This is the bug that had been masking #4.
  4. **Sequence control fragments had no grammar.** `alt`/`else`/`opt`/`loop`/`par` are documented in [user_guide.md](user_guide.md) but the parser had no support at all; only bug #3 hid this, by eating the fragment keywords before they could fail. They now parse as line-scoped markers, so the messages inside them become real edges.

  Covered by [`parser-examples.test.ts`](../packages/core/test/parser-examples.test.ts) — 23 tests, 18 of which fail against the previous parser (verified by stashing the fix, not assumed). It compiles every file in `examples/` and asserts the SVG actually contains nodes, since a file that parses to an empty diagram still returns `ok`. `showcase.sld` compiles too (it holds four diagrams and `compile` takes the first — benign, as previously noted).

  ~~**Still open:** fragments parse but don't *render*.~~ **Now rendered.** Fragments draw as proper UML combined-fragment boxes: an outlined frame around the message range with a notched operator tab (`ALT`/`OPT`/`LOOP`/…), the guard condition beside it, and dashed dividers with guards for each `else`/`critical` section. The pipeline: the parser emits a dedicated `FragmentMarker` AST node (not a discarded comment); [`sequence.ts`](../packages/core/src/diagrams/sequence.ts) pairs each opener with its `end`, tagging every message with the fragment stack it falls inside and recording `[firstEdge, lastEdge)` spans + section splits on `ir.metadata`; [`custom-layout.ts`](../packages/core/src/render/custom-layout.ts) resolves those spans to pixel boxes once message Ys are known, insetting nested fragments by containment depth, and hands them back via a new `metadataPatch` on `CustomLayoutResult`; and [`renderSequenceFragment()`](../packages/core/src/render/custom-renderers.ts) draws the box behind the message arrows. Nesting works (a `loop` containing an `opt` draws inset). Verified by rendering the OAuth example to PNG and inspecting it, plus tests asserting the span/section IR and the rendered tab/divider markup.
- **BPMN start/end events are inferred, not declared.** `(…)` is one shape for both ends of a process, so the plugin settles orientation from edge topology (no incoming = start, no outgoing = end). That matches how a reader parses the picture, but a disconnected event node stays `intermediateEvent`. An explicit `startEvent`/`endEvent` type keyword still overrides it.

## 4. Positioning (from market.md)

> "Keep your Mermaid. SelDiA keeps it true."
> The diagram engine agents use to render, validate, and maintain any diagram-as-code format in your repo.

Target: teams whose architecture docs/ADRs/runbooks drift out of date faster than anyone hand-fixes them. That's a problem Mermaid can't solve (no IR, no diagnostics, no sync) and PlantUML won't (no markdown-native path, no agent story). The wedge is drift, not drawing; the category is *engine*, not *format* — see [market.md §5](market.md#5-positioning--the-category-change) for the full reasoning and the risk that comes with it.
