# SelDiA — Market & Position Analysis

**Date:** 2026-07-16
**Scope:** Competitive position vs. Mermaid, PlantUML, D2, Excalidraw — and where the real leverage is.

---

## 1. The market as it actually is

The diagrams-as-code market in 2026 is **not** an open field. It has a settled shape:

> *"Mermaid won the README and the markdown ecosystem; PlantUML won the engineering whiteboard and the IDE."* — [DEV, Mermaid vs PlantUML in 2026](https://dev.to/levi_liu/mermaid-vs-plantuml-in-2026-which-to-pick-for-engineering-docs-59dm)

| Player | Won because | Weakness |
|---|---|---|
| **Mermaid** | GitHub/GitLab/Notion render it natively. No build step. | Weak layout, limited control, shallow UML/C4 |
| **PlantUML** | 2009-era maturity, formal UML + serious C4, enterprise trust | Java runtime, dated output, no markdown-native path |
| **D2** (Terrastruct, 2022) | TALA layout engine beats dagre/GraphViz; modern aesthetics | Requires a compile step → can't ride GitHub |
| **Excalidraw** | Hand-drawn aesthetic + frictionless collaboration | Not diagrams-as-code; no text source of truth |

The decisive market fact, and the one that should drive strategy:

**Distribution beat capability, twice.** D2 is *technically superior* to Mermaid on layout and is still losing — because "[D2 diagrams require a separate compilation step](https://infrasketch.net/blog/best-diagram-as-code-tools-2026)" and therefore can't ride GitHub's native rendering. Mermaid won on being *already there*, not on being good.

**This is the single most important lesson for SelDiA.** SelDiA is in D2's structural position, not Mermaid's: better output, no native rendering on the platforms where diagrams get consumed. Competing on feature count against Mermaid is the exact strategy that D2 has been losing with for four years.

## 2. What SelDiA actually has

Verified against the codebase, not the README:

- **30 diagram types** in the `DiagramType` enum ([ir/types.ts:15](../packages/core/src/ir/types.ts#L15)) — marketed as "21+" because C4's 4 levels and charts' 5 variants collapse to one each. Genuinely broader than Mermaid (~15) or PlantUML. Native Gitgraph, DMN, Sankey, Form, Wireframe, Cloud have no clean Mermaid equivalent.
- **Live editing in VS Code's Markdown preview** — drag-to-move, double-click-to-rename, syncing back to source. No competitor does this.
- **Rough.js hand-drawn rendering** + 5 themes.
- **A Copilot/agent skill** ([.github/skills/seldia-dsl](../.github/skills/seldia-dsl/SKILL.md)) that teaches an LLM the DSL.
- Modern TypeScript plugin architecture, synchronous rendering, LSP, PDF export.

### An honest correction to the prior internal analysis

The earlier internal memo concluded **"SelDiA's moat is edit mode."** I think that is wrong, and it matters enough to say plainly:

1. **Edit mode is a feature, not a moat.** It's unmatched *today* because no one has built it, not because it's hard to copy. Mermaid Chart (the commercial arm) ships visual editing already. A moat is something a competitor *can't* follow you into; this is a head start measured in quarters.
2. **It's confined to one host.** The advantage only exists inside VS Code's Markdown preview. That's a real audience, but it's a fraction of where diagrams are *read* — GitHub, GitLab, Notion, Confluence, PR reviews.
3. **It optimizes the wrong verb.** Edit mode makes *hand-authoring* nicer at exactly the moment hand-authoring is being displaced (§3).

Edit mode is worth keeping and polishing. It should not be the strategy.

## 3. The actual leverage: be the format AI writes *and reads*

This is the finding that should reshape the roadmap.

> *"More diagrams will be created in the next two years than in the previous twenty. Most of them will be generated by AI."*
> *"AI doesn't just generate diagrams now. It reads them. It executes against them. It uses them as specifications: inputs to a process, not outputs of one."*
> — [Mermaid Chart](https://test-docs.mermaidchart.com/blog/posts/claude-to-mermaid-ai-generated-diagrams)

Three consequences follow, and they invert the usual competitive logic:

**a) "Easy for beginners" stopped being a moat.** Mermaid's DSL simplicity mattered when humans typed every arrow. When an LLM emits the syntax, DSL ergonomics stop being a human-adoption barrier and become a *machine-precision* question: which language lets a model express intent unambiguously and get a correct diagram back? SelDiA's structured, block-scoped, per-type grammar is *better* raw material for a model than Mermaid's arrow soup — and SelDiA already has an LSP, which means **machine-checkable diagrams**. Mermaid fails silently or renders garbage; SelDiA can hand a model diagnostics and let it self-correct.

**b) Round-tripping is the unclaimed high ground.** Everyone can generate a diagram from a prompt — that's commodity, and Mermaid has the training-data advantage there (every LLM already knows Mermaid; none know SelDiA). The unsolved half is the *return trip*: diagram → structured meaning an agent can reason over, mutate, and write back. SelDiA has the one asset that makes this tractable: **a real IR** ([ir/types.ts](../packages/core/src/ir/types.ts)) sitting between text and pixels. Mermaid has a parser bolted to a renderer. PlantUML has a Java monolith. An IR + LSP + bidirectional sync is precisely an **agent-editable diagram**, and SelDiA is accidentally two-thirds of the way there.

**c) The training-data gap is the countervailing risk, and it's severe.** Every frontier model writes Mermaid from memory. None write SelDiA. This is a *distribution* problem in new clothes, and it's the same wall D2 hit. The skill file is the right instinct but too small a lever on its own.

### The strategic bet

> **Mermaid is the format AI writes. SelDiA should be the format AI maintains.**

Generation is a solved, commoditized, one-way act. Maintenance — keeping a diagram true as the system changes — is unsolved, recurring, and where the value compounds. It also plays directly to what SelDiA already is: an IR with a type system, diagnostics, and bidirectional sync. That's not a diagram renderer; it's the substrate for a diagram that an agent can be *held accountable to*.

## 4. Recommended moves, ranked by leverage

### Tier 1 — Do these

**1. Mermaid import/export. This is the highest-leverage item in the document.**
It simultaneously fixes both structural problems: it neutralizes the training-data gap (any LLM writes Mermaid → SelDiA ingests it → renders it better) and it removes the adoption cliff (`seldia import`, no rewrite, no lock-in — export back out to render on GitHub). D2 never did this and D2 is stuck. *Do not skip this to build another diagram type.*

**2. Solve the rendering-distribution problem explicitly.**
SelDiA cannot beat GitHub's native Mermaid support, so stop trying to and route around it: a GitHub Action that renders `.seldia` blocks to committed SVG on push, plus the `<seldia-viewer>` web component. Diagrams must be *readable* where they're reviewed or the tool stays a personal one.

**3. Agent-facing diagram maintenance — the actual bet.**
An MCP server / CLI surface exposing the IR: query a diagram ("what depends on auth-service?"), mutate it structurally, validate it, write it back with diagnostics. This is the thing no competitor can copy quickly, because it requires the IR they don't have.

**4. Persistent manual positions.**
Carried from the prior analysis and still correct — drag-to-edit that loses positions on re-render is worse than no drag-to-edit. If edit mode stays, it must not lie.

### Tier 2 — Real, but only after Tier 1

Themes/palette swapping · edge editing · macro/include system · export to semantic formats (BPMN XML, SQL DDL) · diagram diffing for PRs.

### Tier 3 — Resist for now

More diagram types. **SelDiA already has 30 and is losing to tools with 15.** Type count is not the constraint; distribution is. Adding type 31 is the most comfortable and least useful thing the project could do next.

## 5. Positioning — the category change

**The surgical move: stop being a third diagram *format* and become the diagram *engine* that runs everyone's — Mermaid and PlantUML included.** You don't beat an incumbent format in a format war; you demote it to an input your engine supports.

### The frame inversion

- **Old frame (losing):** "SelDiA vs. Mermaid" — a format war against a format with native GitHub rendering and total LLM training-data coverage. This is D2's four-year losing script.
- **New frame (winning):** "SelDiA runs your Mermaid." Users keep their format, their GitHub rendering, their AI-generation habits. SelDiA sits underneath as the engine that parses, validates, queries, and keeps diagrams true — the layer neither competitor has an architecture for.

### Why this wins rather than merely competes

1. **It converts both competitors' strengths into distribution.** Every Mermaid diagram in every repo becomes SelDiA's addressable market on day one — no rewrite, no lock-in, no training-data problem. Mermaid's ubiquity stops being the wall and becomes the funnel.
2. **It's structurally uncopyable by the incumbents.** Mermaid can't become an engine — it's a parser bolted to a renderer with a decade of syntax debt. PlantUML can't — a Java monolith with no markdown path. SelDiA's IR is the only asset in this market that supports the engine position.
3. **It rides the real trend.** Most diagrams will soon be AI-generated and AI-read (§3). In that world nobody wins by owning the syntax humans type; the winner owns the layer agents call. Formats commoditize; engines don't.

### The pitch

> **"Keep your Mermaid. SelDiA keeps it true."**
> The diagram engine agents use to render, validate, and maintain any diagram-as-code format in your repo.

The three-word test: Mermaid is *a format*. PlantUML is *a tool*. **SelDiA is *the engine*.** Positioned this way, SelDiA never argues syntax again — the SelDiA DSL becomes the engine's native format for those who want its full power, not the price of admission.

**Avoid:** "The tool with the most diagram types." Type breadth is real but it's a *format-war* pitch — it concedes the losing frame. Same for "better-looking output" (D2's failed pitch).

Target: engineering teams whose architecture docs, ADRs, and runbooks drift out of date faster than anyone hand-fixes them. The wedge is *drift*, not drawing — a problem Mermaid structurally cannot solve (no IR, no diagnostics, no sync) and PlantUML won't (no markdown-native path, no agent story).

**The honest risk, restated under the new frame:** the engine position is only credible if Mermaid ingestion is excellent — not a demo-grade importer. A leaky bridge re-opens the format war. Mermaid import is therefore not one feature among several; it is the positioning itself, made executable.
