# SelDiA — Design & Architecture Review (2026-07-14)

Scope: the reported Markdown‑preview issue, plus a review of the SelDiA DSL
design and the project architecture, with tests run and concrete issues fixed.

---

## 1. Reported issue — Markdown preview opened a separate panel

**Symptom.** Opening *Preview arch.md* did not render `seldia` blocks inline;
a separate **“SelDiA Diagram Preview”** tab appeared instead.

**Root cause.** `CoreEngine.compile()` is declared `async` (returns a
`Promise`), but VS Code’s `extendMarkdownIt` fence renderer **must be
synchronous**. The markdown‑it plugin called `engine.compile(code)` and read
`result.ok` on the returned `Promise` (always `undefined`), fell into the error
branch, and threw on `result.errors.map(...)`. The inline render therefore
failed and the UX fell back to the standalone webview panel.

**Fixes (implemented).**
- Added `CoreEngine.compileSync()` (the pipeline was already fully synchronous);
  `compile()` now delegates to it. — `packages/core/src/engine.ts`
- The markdown‑it plugin now uses `compileSync` and renders a single inline
  container with three modes. — `packages/vscode-ext/src/markdown-preview/plugin.ts`
- Removed the dead standalone panel (`markdown/preview-panel.ts`, the source of
  the “SelDiA Diagram Preview” tab; it was no longer wired into activation).

**Result.** `seldia` blocks render **inline** in the built‑in Markdown preview
with a **Preview / Code / Edit** toggle — no separate panel.

### Edit mode
The preview now supports, in place:
- **Preview** — rendered SVG with zoom / reset / export.
- **Code** — the DSL source.
- **Edit** — drag a node to move it; double‑click a node to rename it. Gestures
  are written back to the underlying `seldia` block via extension commands
  (`seldia.moveNode`, `seldia.editNodeLabel`, `seldia.editNodeAttr`) invoked
  through `command:` URIs — the sanctioned channel from the built‑in preview to
  the host. All DSL manipulation lives in pure, unit‑tested functions
  (`packages/vscode-ext/src/edit/dsl-edit.ts`).

Node identity is carried end‑to‑end: the renderer stamps
`data-seldia-node-id` / `data-seldia-edge-id` on the SVG, and each block carries
a stable content‑hash id shared by the plugin, the preview script, and the host.

## 2. DSL design review — findings & fixes

### 2.1 Inline style / attribute blocks were not implemented — **FIXED**
The parser hard‑coded `style: undefined` for every node and edge, and
`parseStyleBlock` explicitly “skipped style items”. So the **entire** documented
styling and layout‑hint system (user_guide §4.7, §6.3; arch §3.3) silently did
nothing.

Implemented a real `parseAttrBlock` / `parseAttrValue` and wired it into node,
typed‑node, participant, inline‑node and edge declarations. Node/edge style
blocks now parse (`{ fill: "#fff", roughness: 2, shadow }`), including bare
flags and simple arrays.

### 2.2 Manual position overrides were ignored — **FIXED**
`layout()` always grid‑placed nodes. Added `resolvePosition()`, which honors a
manual `{ x, y }` on a node before falling back to plugin position then the
default grid. This is what makes **drag‑to‑move** persist.

### 2.3 Arrows required surrounding spaces — **FIXED**
Identifiers greedily consumed `-`, so `a-->b` tokenized as `a--`. The identifier
reader now stops before a hyphen that begins an arrow, while still allowing
hyphens inside names (`my-node`). `a-->b`, `a->b`, and `my-node --> other` all
parse.

### 2.4 Nested object values do not tokenize — **DOCUMENTED (not fixed)**
The tokenizer turns any `{` immediately after `:` into a diamond‑shape token, so
`layout: { x, y }`, `palette { … }`, chart `data { … }`, and C4 nested
`{ description: … }` blocks mis‑tokenize. This is a structural tokenizer
ambiguity (a node‑shape `{…}` vs an object value `{…}`) and a larger change than
this pass should carry.

**Consequence for users today:** use the **flat** form the implementation
supports — e.g. `a: (Start) { x: 300, y: 200 }` instead of the documented
`{ layout: { x: 300, y: 200 } }`. The Edit‑mode writer emits the flat form.
Recommendation: either make the tokenizer context‑aware (track body vs
attribute‑block context on a brace stack) or update the docs to the flat form.

### 2.5 Documented DSL » implemented DSL — **DOCUMENTED**
The parser implements a pragmatic subset. Many constructs shown in
`docs/user_guide.md` (per‑type keyword grammars for DMN rules, gantt task dates,
form fields, chart `data/series`, sankey `flow`, C4 rich metadata, class member
bodies, etc.) are accepted only loosely or fall back to generic node/edge
handling. This is fine as a subset, but the guide currently reads as if all of
it is fully supported. Recommend aligning the guide with the implemented grammar
(or marking aspirational sections).

### 2.6 File extension mismatch — **DOCUMENTED**
`user_guide.md` says diagrams use `.seldia`; the extension registers `.sld`
(and all `examples/` use `.sld`). Pick one and make the docs consistent.

## 3. Architecture review — findings

### 3.1 `@seldia/render`, `@seldia/layout`, `@seldia/interaction` are unused by core
`@seldia/core`’s `engine.ts` reimplements layout (`resolvePosition`,
`computeWaypoints`) and SVG rendering (`renderToSvg`) inline and imports none of
those packages. The elaborate class designs in `arch.md §5.2–5.4` do not match
the shipped engine. Either route the engine through those packages (the arch’s
intent) or acknowledge the engine as the real renderer and trim the packages.
The internal renderer is adequate but basic (grid layout, polyline edges, a
single sketch filter).

### 3.2 “Bidirectional sync” utilities from arch §5.8.5 are largely absent
`utils/source-map.ts`, `utils/code-generator.ts`, `utils/diff-patcher.ts` do not
exist (only `sync-controller.ts`). The new `edit/dsl-edit.ts` now provides a
pure, tested substitute for the Markdown‑preview edit path.

### 3.3 Plan/status accuracy
`docs/plan.md` marks Phases 0–10 “all complete, tested, and committed”, but until
this pass there were **no unit tests** in any package (only a root integration
script) and the Markdown inline‑preview path was broken. Several ✅ items are
stubs (CLI `md2pdf`, PNG/PDF export, markdown injection grammar `V2`, ELK layout
`A5`). Recommend reconciling the plan with reality.

### 3.4 Missing Markdown injection grammar
No `seldia-markdown.tmLanguage.json`, so `seldia` fences get no syntax
highlighting in the Markdown *editor* (rendering in the *preview* is unaffected).

## 5. Recommended next steps (not done in this pass)
1. Make the tokenizer context‑aware to support nested object values (§2.4), then
   restore the documented `layout: { x, y }` / palette / chart syntaxes.
2. Decide the fate of `@seldia/render|layout|interaction` (integrate or remove).
3. Reconcile `docs/plan.md` and `docs/user_guide.md` with the implemented subset;
   fix the `.sld` vs `.seldia` mismatch.
4. Add the Markdown injection grammar for editor‑side highlighting.
5. Extend Edit mode: edge rerouting, add/delete node, style panel (arch §5.8.3).
